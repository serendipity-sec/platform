# 실험 1 — capability diff 검증

**질문**: 기존 정적 스캐너의 베이스라인이 *findings*가 아닌 *capability* 변화를 놓치는가?

이 프로젝트의 차별화 주장 전체가 이 가설 위에 서 있다. 틀리면 주제를 다시 잡아야 한다.

| | |
|---|---|
| 실험일 | 2026-09-17 (round1, round2) |
| 도구 | NVIDIA SkillSpector v2.11.2 (Apache-2.0), `--no-llm` 정적 분석 모드 |
| 표본 | 4개 유형 × 11쌍 |
| 결과 | **11쌍 중 9쌍에서 capability 변화를 놓침** |
| 종합 보고 | [RESULTS-combined.md](RESULTS-combined.md) |

---

## ⚠️ 여기 있는 코드에 대하여

`pairs/` 아래 파일들은 **의도적으로 위험해 보이게 작성한 테스트 자료**다.
외부 전송, 파일 접근 범위 확대, 동적 실행, 자격증명 경로 열람 같은 코드가 들어 있다.

- **실제 악성 페이로드는 없다.** 로컬 테스트 엔드포인트만 사용한다.
- **실행하지 말 것.** 스캐너 입력으로만 쓴다.
- 실제 자격증명·토큰·개인정보를 넣지 말 것. 커밋 전 `secret-scan` 워크플로가 검사한다.
- 외부에 재배포하지 말 것. 평가용 자료다.

`CONTRIBUTING.md`의 "검사 대상 자료를 다룰 때" 항목을 따른다.

## 표본 설계

| 유형 | 내용 | 쌍 |
|---|---|---|
| A | 네트워크 전송이 새로 생김 | A1 A2 A3 |
| B | 파일 접근 범위가 넓어짐 | B1 B2 B3 |
| C | 실행 권한이 새로 생김 | C1 C2 |
| D | 자격증명에 접근하게 됨 | D1 D2 D3 |

각 쌍은 `v1/`(기준)과 `v2/`(capability가 넓어진 버전)로 구성한다.
**v2는 v1에서 한 종류의 capability만 추가한다.** 여러 개를 동시에 바꾸면 무엇이 탐지를
유발했는지 알 수 없다.

### 아직 없는 것 — 다음 라운드에서 반드시 채울 것

- [ ] **무변화 대조군** — capability는 그대로 두고 변수명·주석·함수 분리만 바꾼 쌍 3~4개.
      이게 없으면 `7 → 7`이 "변화를 놓쳤다"인지 "이 스캐너는 원래 7점을 준다"인지 구분할 수 없다.
      **현재 결과 해석의 가장 큰 구멍이다.**
- [ ] **역방향 쌍** — v1이 위험하고 v2가 그 위험을 제거한 경우 점수가 내려가는지
- [ ] **실제 스킬 버전 쌍** — 우리가 작성한 표본이라 "못 잡게 썼다"는 반론이 가능하다.
      ClawHub 데이터셋(MIT, 66,200행)의 실제 버전 쌍으로 재현하면 이 반론이 사라진다
- [ ] **두 번째 도구** — AgentShield로 규칙 파일(CLAUDE.md) 대상 동일 실험 4~6쌍

## 재현 방법

```bash
# 1. SkillSpector 설치 (Apache-2.0)
#    https://github.com/nvidia/skillspector
pip install skillspector          # 또는 저장소 README의 설치 방법

skillspector --version            # v2.11.2 로 고정해 비교할 것

# 2. 각 쌍의 v1 / v2 를 따로 스캔
skillspector scan round2/pairs/A2/v1 --no-llm --format json > round2/results/A2-v1.json
skillspector scan round2/pairs/A2/v2 --no-llm --format json > round2/results/A2-v2.json

# 3. risk_assessment.score 와 issues 배열을 비교
```

### 왜 `--baseline`을 쓰지 않았나

SkillSpector의 `--baseline`은 **파일 경로 기반 fingerprint**를 쓴다.
v1과 v2가 서로 다른 디렉터리에 있으면 매칭이 어긋나 비교가 성립하지 않는다.
그래서 v1 원본 스캔과 v2 원본 스캔을 직접 비교했다.

> **보완 필요**: 같은 경로에 v1을 두고 baseline을 뜬 뒤 v2로 덮어쓰고 재스캔하는,
> 도구가 의도한 워크플로도 최소 한 쌍은 재현해야 한다. 그러지 않으면
> "정식 사용법을 안 써보고 한계라고 했다"는 반론을 막을 수 없다.

## 판정 기준

| 판정 | 조건 |
|---|---|
| **잡힘** | v2에서 새 finding이 생겼거나 risk score가 유의하게 올라감 |
| **놓침** | v1과 v2의 finding·score가 동일 |
| **검사 불가** | 스캐너가 대상을 파싱하지 못했거나 결과를 내지 못함 |

> **검사 불가를 "놓침"으로 집계하지 않는다.** 이 프로젝트는 검사 불가 자료를 정상으로
> 집계하지 않겠다고 선언했고, 우리 실험에도 같은 규율을 적용한다.
>
> 현재 round2의 B2가 `0 → 0`으로 다른 쌍(`7 → 7`)과 다르다. 스캐너가 대상을 제대로
> 파싱하지 못했을 가능성이 있으므로 **원본 출력을 확인해 재분류 여부를 판단해야 한다.**

## 숫자를 쓸 때

표본이 11개다. **"81.8%"보다 "11쌍 중 9쌍"으로 적는다.** 소수점 한 자리는 과잉 정밀이다.

유형별 비율(A 100%, C 50%, D 67%)은 각 2~3개 표본에서 나온 값이므로
정밀한 비율이 아니라 **"혼재되어 있다"는 정성적 신호로만** 읽는다.

ClawHub 논문의 "81.9%"(세 스캐너 중 한 곳만 지목한 스킬 비율)와 숫자가 비슷하지만
**완전히 다른 것을 재는 값이다.** 나란히 인용할 때는 반드시 구분을 명시한다.
