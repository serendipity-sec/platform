## Round1 결론의 수정

Round1에서는 "실행(exec) 계열은 이미 잘 잡힌다"고 결론 내렸다. **Round2가 이걸 반증했다.**

- `subprocess.run(shell=True)` (C1) → 잡힘. AST 기반 규칙(AST4 Dangerous Code Execution)이 `subprocess` 같은 **알려진 위험 함수 호출**을 이름만 보고 반응한다.
- `importlib.util` 기반 동적 모듈 로드·실행 (C2) → **놓침**. 똑같이 "설정 파일이 가리키는 코드를 실행한다"는 capability인데, 함수 이름이 스캐너의 알려진 위험 함수 목록(`subprocess`, `os.system`, `eval` 등으로 추정)에 없으면 패턴 매칭에 안 걸린다.

**즉 "실행이 잡힌다"가 아니라 "스캐너가 이미 아는 이름의 함수 호출만 잡힌다"**가 정확한 설명이다. 이건 원래 가설보다 훨씬 더 팀 프로젝트에 유리한 결론이다 — capability 자체가 아니라 **표면적 구현(어떤 함수/라이브러리를 썼는지)에 의존하는 탐지**라는 근본적 한계를 보여주기 때문이다.

자격증명(D) 유형도 비슷한 패턴이다: 일반적인 env var(D1)나 SSH 키 해시(D2)는 놓쳤지만, `~/.aws/credentials`라는 **잘 알려진 특정 경로 문자열**을 여는 코드(D3)는 잡혔다(PE3 Privilege Escalation). 이것도 "자격증명 접근이라는 capability를 이해해서" 잡은 게 아니라 **알려진 민감 경로 문자열 매칭**으로 추정된다.

## 재정의된 차별화 포인트

> 기존 정적 스캐너는 **"capability의 의미"가 아니라 "알려진 함수 이름·알려진 경로 문자열"에 반응한다.** 같은 capability(외부 전송, 파일 스코프 확장, 임의 실행, 자격증명 접근)라도 구현 방식이 스캐너의 알려진 패턴 목록과 다르면 그대로 통과한다.

이건 팀이 처음 세운 가설("규칙을 안 건드리면 capability 변화를 놓친다")보다 한 단계 더 나아간, **왜** 놓치는지에 대한 설명이다. 계획서에 쓸 수 있는 문장:

> "우리는 새 함수 이름이나 새 위험 패턴을 하나 더 추가하는 스캐너를 만들지 않는다. 대신 코드가 실제로 요구하는 접근·연결·실행의 **의미**(어떤 목적지로 나가는가, 어떤 파일 종류에 닿는가, 실행이 어디서 오는 입력에 의해 결정되는가)를 버전 간에 비교해서, 표면 구현이 달라도 같은 종류의 capability 확장이면 잡아내는 계층을 만든다."

## 방법론 각주 (round1과 동일하게 유지)

- `--baseline` 억제 기능은 파일 경로 기반 fingerprint를 써서 v1/v2가 별도 디렉터리면 매칭이 어긋난다. 이번에도 v1 raw scan과 v2 raw scan을 직접 비교하는 방식으로 판정했다.
- 표본이 11개로 늘었지만 여전히 작다. 특히 C, D는 각 2~3개뿐이라 "50%/67%"라는 숫자를 정밀한 비율로 해석하면 안 되고, "혼재되어 있다"는 정성적 신호로만 읽어야 한다.
- 모든 테스트는 SkillSpector 한 도구로만 진행했다. AgentShield(CLAUDE.md류 대상)나 다른 스캐너에서는 다른 패턴이 나올 수 있다.
- 모든 코드는 무해하게 동작하도록 작성했다(실제 악성 페이로드 없음, 로컬 테스트 엔드포인트만 사용).
