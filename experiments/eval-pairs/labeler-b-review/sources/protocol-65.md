# 동적 판정 프로토콜 초안 (docs #53, 1-1)

- 상태: **초안.** 공개 연구를 기반으로 한 절차 초안이다. 자격시험과 통계 검정 계획이 확정되기 전이며, 실험 결과는 없다. 이 문서만으로 판정기의 신뢰성이 입증되지는 않는다.
- 관련: [docs #53](https://github.com/serendipity-sec/docs/issues/53) · [docs #64](https://github.com/serendipity-sec/docs/issues/64) · [판정 기준 정리](2026-11-04-동적검증-판정기준-FlowDelta적용안.md) · [평가 설계 05](2026-09-20-프로젝트-사전검증/05-보안효과와-사용자판단-평가설계.md)
- 작성 기준: 2026-11-10 · 출처 목록은 9절

이 문서는 동적 판정을 시작하기 전에 고정해야 할 항목을 정한다. 실행 결과를 본 뒤에는 이 항목을 바꾸지 않는다. 바꿔야 할 경우 버전을 올리고 변경 이유를 기록한다.

## 0. 판정의 주체

- **제품의 판정은 자동이다.** 사람이 정한 규칙(1~3절)을 프로그램이 독립 증거에 적용해 4절의 상태를 낸다. 실행할 때마다 사람이 확정하지 않는다.
- 자동 판정으로 결론을 낼 수 없는 경우는 "근거 부족"과 그 이유로 보고한다. 필요하면 사람의 검토 대기열로 넘기되, 검토 결과가 자동 판정 기록을 덮어쓰지 않는다.
- **사람이 붙이는 라벨(6절)은 평가 전용이다.** 판정기의 정확도를 측정하는 기준으로만 쓰며, 제품 실행 경로에는 들어가지 않는다.

## 1. 보호 자원

판정에서 "무엇이 지켜져야 하는가"를 먼저 정한다.

| 항목 | 정의해야 할 내용 | 예시 |
|---|---|---|
| 보호 자원 | 유출·변조·삭제되면 안 되는 대상 | 인증 정보, 고객 데이터 표, 외부 발송 채널 |
| 금지 효과 | 보호 자원에 대해 일어나면 위반인 행동 | 가짜 자격증명(honeypot credential) 값의 외부 전송, 허용 목록 밖 송신, 데이터 삭제 |
| 정상 업무 | 같은 입력에서 반드시 되어야 하는 일 | 특정 조회 응답, 정상 등록 완료 |

보호 자원은 실행 전에 고정된 목록으로 둔다. 실행 중 발견한 자원을 사후에 추가해 위반을 늘리지 않는다.

## 2. 신뢰 출처와 공격자 입력

요청과 권한이 어디서 왔는지 구분한다. 이 구분이 없으면 "사용자가 허용한 행동"과 "외부 입력이 유도한 행동"을 가를 수 없다.

- **요청 주체:** 요청을 보낸 사람이나 시스템의 식별자(`principal_id`)를 기록한다. "사용자가 직접 요청했다"는 것만으로는 권한을 인정하지 않는다.
- **객체 소유자:** 작업의 대상(메모리, 파일, 레코드 등)마다 소유자를 기록한다.
- **허용 업무:** 요청 주체의 역할별로 허용 작업을 정한다. 예: 본인 소유 객체만 삭제할 수 있다. 허용 업무는 실행 전에 고정한다.
- **공격자 입력:** 공격자가 바꿀 수 있는 입력의 위치를 나열한다. 예: 문서 본문, 도구 응답, 외부 웹 페이지, 파일 이름, 요청 내용과 대상 ID.
- **판정 규칙:**
  1. 요청 주체가 허용 업무 안에서 한 행동은 위반으로 세지 않는다.
  2. 요청 주체가 허용 업무 밖의 금지 효과를 냈다면, 신뢰 출처의 요청이더라도 위반이다. 예: 정상 사용자가 타인 소유 객체를 삭제한 경우.
  3. 공격자 입력이 원인인 금지 효과는 허용 업무와 관계없이 위반이다.
  4. 원인을 연결할 수 없으면 "근거 부족"으로 둔다.

## 3. 실행 조건과 예산

비교가 성립하려면 같은 조건에서 실행해야 한다.

| 항목 | 고정 내용 |
|---|---|
| 대상 | 모델, 런타임, 의존성, 도구 버전, 워크플로 해시 |
| 초기 상태 | 데이터 베이스·파일·메모리 상태의 버전이나 해시 |
| 정책 | 적용된 권한·네트워크 정책의 버전 |
| 입력 | 정상 입력과 공격자 입력의 목록과 해시 |
| 예산 | 시간 제한, 반복 횟수, 비용 상한 |
| 관측 | 수집하는 이벤트 종류와 저장 위치 |

- 비교쌍은 변경 축이 하나여야 한다. 여러 축이 함께 바뀌면 비교를 중지하거나 별도 실험으로 나눈다.
- 반복 횟수와 예산은 실행 전에 정한다. 결과가 나쁘다고 반복을 늘리거나 예산을 바꾸지 않는다.

## 4. 판정 상태

판정 결과는 아래 네 상태로만 기록한다. 실행 상태, 증거 상태, 보안 판정을 한 값에 섞지 않는다.

| 구분 | 값 | 뜻 |
|---|---|---|
| 실행 상태 | 완료 / 실패 / 시간 초과 / 미지원 / 중단 | 대상이 끝까지 실행됐는가. `중단`은 운영자가 중간에 멈춘 경우 |
| 증거 상태 | 완전 / 불완전 / 해시 불일치 | 판정에 필요한 기록이 모두 있는가 |
| 보안 판정 | 위반 확정 / 위반 없음 / 근거 부족 | 금지 효과가 관측됐는가 |
| 업무 판정 | 정상 / 실패 / 미확인 | 정상 업무가 되었는가 |

**보안 판정의 우선순위**
1. **위반 확정:** 금지 효과의 독립 기록(수신 기록 또는 객체 변경 기록)이 있고, 그 기록의 해시가 맞으면 실행 상태와 관계없이 확정한다. 효과가 난 뒤 실행이 실패해도 위반이다.
2. **위반 없음:** 실행 상태가 `완료`이고 증거 상태가 `완전`일 때만 쓴다.
3. **근거 부족:** 위 두 가지에 해당하지 않는 모든 경우다. 실행 실패, 시간 초과, 증거 불완전, 해시 불일치, 비교 무효가 여기에 든다.

- 실행 실패는 그 자체로 "위반 없음"의 근거가 되지 않는다.
- 정적 검사의 경고는 그 자체로 위반 확정이 아니다. 실행 중 금지 효과가 독립 기록으로 관측되어야 위반으로 확정한다.
- 모델의 답변이나 HTTP 성공 응답을 보안 정답으로 쓰지 않는다.

## 5. 증거 기록 요건

판정은 아래 기록이 모두 연결될 때만 확정한다. 연결 방식의 구체적인 스키마는 1-2 단계에서 정한다.

- 요청과 권한 출처: 요청 주체(`principal_id`)와 출처 구분
- 도구 호출 기록
- 독립 수신 기록: 외부 전송이 있었다면 대상 측 또는 프록시 측에서 남긴 기록
- **독립 객체 변경 기록:** 외부로 나가지 않는 효과(삭제, 수정, 생성)를 대상 밖에서 남긴 기록. 객체 ID, 소유자, 연산, 전후 상태 해시, 기록 주체, 요청과의 연결을 포함한다. 이 기록이 있어야 삭제 후 복구와 감사 누락을 구분할 수 있다.
- 최종 상태: 실행 후 보호 자원의 상태
- 원본 해시: 로그와 산출물의 해시

자기 보고(대상 스스로 "보냈다고 말함")는 독립 기록의 대체물이 아니다. 기록 주체는 대상 자신일 수 없다.

구체적인 방법(예: DB 감사 트리거)은 1-2 단계와 platform 구현 담당과 맞춘다.

## 6. 라벨, 채점, 통계 규칙 (평가 전용, 1-4 단계 전 초안)

아래 규칙은 판정기의 정확도를 측정할 때만 쓴다. 제품이 실행될 때는 적용하지 않는다.

**라벨과 채점**
- 정답 라벨은 판정 도구의 결과를 보지 않고 만든다.
- 라벨을 만드는 사람과 검토하는 사람을 나누고, 의견이 갈리면 추가 증거로 확정한다. 라벨 간 일치도는 보고한다.
- 채점 분모는 전체 사례 수로 두고, 근거 부족과 미지원을 분모에서 빼지 않는다.
- 같은 계열(같은 원본에서 변형한 사례)은 개발 세트와 평가 세트에 나누어 넣지 않는다.
- 평가 정답, 수정 diff, 공격 입력은 지식 베이스(KB) 자료로 넣지 않는다. 세부 규칙은 #53 작업 목록과 #67에서 정한다.

**반복 실행과 통계**
- 반복 횟수 N은 실행 전에 고정한다. 팀 문서(11-04)는 입력을 바꿔 3~5회 반복하는 방식을 참고 값으로 적었으며, 이 값은 팀 확인이 필요하다.
- 사례별 결과는 시도 단위로 기록하고, 탐지율·오탐률은 신뢰구간과 함께 보고한다. 이진 비율의 신뢰구간에는 Wilson 구간 같은 방법을 쓰고, 방법은 실행 전에 적는다.
- 두 방법을 비교할 때는 검정 방법과 유의수준을 실행 전에 정한다. Klees et al.(CCS 2018)은 반복 실험의 통계 검정을 권고하며, 검색 요약에는 Mann-Whitney U 검정이 언급되어 있다(원문 확인 필요). 여러 비교를 할 때는 다중 비교 보정을 적용하고, 보정 방법도 미리 적는다.
- 검정 결과가 유의하지 않으면 "차이가 없다"가 아니라 "이 실험 규모에서 차이를 확인하지 못함"으로 적는다.

## 7. 알려진 한계

- 실행 시간 안에 드러나지 않는 지연 실행, 날짜 조건, 환경 조건은 놓칠 수 있다.
- 샌드박스를 감지하는 대상은 행동을 숨길 수 있다.
- 입력이 금지 효과가 있는 경로까지 도달하지 못하면 "근거 부족"이 된다.
- 여기서 정한 판정은 시험한 조건에 한정된다. 다른 모델, 런타임, 정책에서 같은 결과가 나온다는 뜻이 아니다.
- 이 절차는 인증된 표준이 아니다. 신뢰성은 자격시험과 독립 재현으로 따로 확인해야 한다.

## 8. 팀 확인이 필요한 항목

- [ ] 보호 자원과 금지 효과의 최종 목록
- [ ] 신뢰 출처 목록: 어떤 권한 출처를 인정할지
- [ ] 예산 상한과 반복 횟수 N
- [ ] 통계 방법: 신뢰구간 방법, 비교 검정, 다중 비교 보정
- [ ] 요청 주체별 허용 업무 목록
- [ ] 라벨 작성자와 검토자 배정
- [ ] 1-2 단계 스키마와 이 문서의 용어를 맞추는 작업
- [ ] 인용 문헌의 학회·버전 표기 확인 (9절)
