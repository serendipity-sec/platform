## 1. 라벨 규칙

**이 절의 라벨은 평가 전용이다.** 제품의 자동 판정 결과가 맞는지 측정하는 정답으로만 쓴다. 제품이 실행될 때 사람이 라벨을 붙이거나 판정을 확정하지 않는다. 자동 판정이 "근거 부족"으로 낸 사례도 평가에서는 라벨을 붙여 집계한다.

### 1.1 누가, 언제 만드나
- 정답 라벨은 **판정기 결과를 보기 전에** 만든다. 판정기 출력이 라벨에 영향을 주면 그 라벨은 쓰지 않는다.
- 라벨러는 최소 2명이다. 두 사람은 서로 독립적으로 라벨을 붙인다.
- 라벨 작성자는 판정기 구현자와 달라야 한다. 장준서(판정기 구현 담당)는 라벨러에서 제외한다.
- **작업 기본값:** 라벨러 A는 #53 교차 재현 담당(@vmaca123), 라벨러 B는 그 밖의 팀원 1명을 제안한다. 실제 배정은 팀원 본인의 수락으로 확정한다.

### 1.2 라벨 값
라벨은 사례마다 아래 값 중 하나다. 판정기 출력과 같은 체계를 쓴다.

| 라벨 | 기준 |
|---|---|
| 위반 확정 | 독립 수신 기록 또는 독립 최종 상태로 금지 효과가 확인됨 |
| 위반 없음 | 실행과 증거가 완전하고, 금지 효과가 확인되지 않음 |
| 근거 부족 | 실행 실패, 시간 초과, 증거 불완전, 해시 불일치, 비교 무효 중 하나 |

- "근거 부족"은 라벨에서도 정답 한 종류로 취급한다. 판정기가 "위반 없음"으로 내면 오판으로 센다.
- 라벨 파일에는 근거(어떤 Receipt, 어떤 FinalState를 봤는지)를 함께 적는다. 근거 없는 라벨은 쓰지 않는다.

### 1.3 불일치 처리
- 두 라벨러가 같은 라벨이면 확정한다.
- 다르면 세 번째 사람이 추가 증거를 보고 확정한다. 세 번째 사람은 두 사람의 근거를 모두 본다.
- 확정 전 불일치는 **일치도 계산에 포함**한다. 불일치를 숨기고 확정 라벨만 보고하지 않는다.

### 1.4 일치도 보고
- 라벨 간 일치도는 Cohen's κ로 보고한다. κ의 계산과 해석 기준은 원문을 확인한 뒤 적는다. **[확인 필요]**
- 일치도가 낮으면 라벨 규칙을 고친 뒤 다시 라벨링한다. 이 경우 규칙 버전을 올리고 변경 이유를 기록한다.

## 2. 분모

| 항목 | 규칙 |
|---|---|
| 전체 사례 | 시도한 모든 사례 수다. 실행을 시작한 사례만 세지 않는다 |
| 근거 부족 | 분모에 포함한다. 정상으로도, 위반으로도 세지 않는다 |
| 미지원 | 분모에 포함하고, 따로 비율을 보고한다 |
| 중단 | 분모에 포함하고, 중단 사유를 기록한다 |

지표 계산은 아래처럼 한다. 근거 부족은 **분자에 넣지 않는다.**

- **탐지율(TPR):** 라벨이 "위반 확정"인 사례 중 판정기가 "위반 확정"으로 낸 비율
- **오탐률(FPR):** 라벨이 "위반 없음"인 사례 중 판정기가 "위반 확정"으로 낸 비율
- **근거 부족 비율:** 전체 중 판정기가 "근거 부족"으로 낸 비율. 따로 공개한다.
- **판정 누락 비율:** 전체 중 판정기가 출력하지 못한 비율. 따로 공개한다.

## 3. 계열 분할

### 3.1 계열이란
**작업 기본값:** 같은 기준 workflow 해시에서 파생된 사례들을 한 계열로 본다. 공격 패턴이 같더라도 기준 workflow가 다르면 다른 계열이다. 계열 안에서 조금씩 바뀐 사례는 독립된 표본이 아니다.

### 3.2 분할 규칙
- **계열 단위로 나눈다.** 같은 계열의 사례는 개발 세트, 검증 세트, 평가 세트 중 한 곳에만 들어간다.
- **작업 기본값 비율:** 계열 수 기준으로 평가 세트 30%, 나머지는 개발 세트 70%다. 검증 세트는 두지 않고, 개발 중 확인은 개발 세트 안에서 교차 검증으로 한다.
- 사례 단위로 무작위 분할하면 정답이 새어 들어갈 수 있다. 이 방식은 쓰지 않는다.
- 세트 배정은 평가 시작 전에 고정하고, 배정표를 파일로 남긴다.

### 3.3 정답 유출 방지
- 평가 세트의 **정답 라벨, 공격 입력 원문, 정답을 짐작할 수 있는 설명**은 개발 중에 판정기 설정이나 규칙에 넣지 않는다.
- 개발 중 규칙을 고칠 때는 개발 세트의 사례만 본다.
- 자격시험 사례(C-01~C-10)는 평가 세트로 쓰지 않는다. 판정 규칙을 확인하는 용도로만 쓴다.

## 4. 평가 동결

- 평가를 시작하기 전에 아래 항목을 고정하고, 해시를 남긴다.
  - 판정 규칙 버전
  - 라벨 파일과 라벨 규칙 버전
  - 평가 세트 배정표
  - 반복 횟수 N과 통계 방법
  - 예산 상한
- 동결 후 바꾸면 **새 평가로 시작**한다. 기존 결과는 "이전 규칙" 결과로 보존하고 삭제하지 않는다.
- 결과를 본 뒤 기준을 바꾸는 것은 허용하지 않는다.

## 5. 통계 규칙

프로토콜 초안 6절의 내용을 구체화한다.

| 항목 | 제안 | 상태 |
|---|---|---|
| 반복 횟수 N | 사례당 3회 (팀 문서 11-04의 하한 값) | 작업 기본값. 동결 전에만 바꿀 수 있다 |
| 이진 비율의 신뢰구간 | Wilson 구간 | 작업 기본값 |
| 두 방법 비교 검정 | Mann-Whitney U (Klees et al.의 권고와 검색 요약에 언급됨) | 작업 기본값. 원문 권고 문구는 확인 필요 |
| 다중 비교 보정 | Holm 보정 | 작업 기본값 |
| 유의수준 | 0.05 | 작업 기본값 |

- 신뢰구간이 0을 포함하면 "차이를 확인하지 못함"으로 보고한다. "차이가 없다"고 쓰지 않는다.
- 사례 수가 적으면 신뢰구간이 넓어진다. 보고서에 사례 수를 항상 함께 적는다.

## 6. 집계 재현 방법

다른 팀원이 같은 표를 다시 만들 수 있어야 한다.

1. **원시 기록을 보관한다.** 시도마다 판정기 출력, 실행 상태, 증거 상태, 원본 파일 해시를 저장한다 (연결 계약 초안 참고).
2. **집계 스크립트를 저장소에 둔다.** 작업 기본값은 platform 저장소의 실험 디렉터리(`platform/experiments`, #54 참고)다. 입력은 원시 기록 파일과 라벨 파일이고, 출력은 표와 지표다. 스크립트는 실행 환경(버전, 의존성)을 고정한다.
3. **매니페스트를 만든다.** 입력 파일 목록과 각 해시, 스크립트 해시, 실행 날짜를 적는다.
4. **재현 확인.** 다른 팀원이 매니페스트 기준으로 같은 표를 만들고, 숫자가 같은지 확인한다.
5. **중간 실패를 숨기지 않는다.** 실행 실패, 미지원, 판정 누락 수를 표의 맨 아래에 항상 함께 적는다.

## 7. 확정 상태

**작업 기본값으로 정한 것 (팀 결정 아님, 동결 전에만 바꿀 수 있음)**
- 반복 횟수 N = 3
- 계열 정의 = 같은 기준 workflow 해시에서 파생된 사례
- 세트 비율 = 계열 기준 평가 30%, 개발 70%
- 다중 비교 보정 = Holm, 유의수준 = 0.05
- 집계 스크립트 위치 = `platform/experiments`
- 라벨 규칙: 판정기 결과를 보기 전에, 두 명이 독립적으로 라벨링

**팀원 수락이 필요한 것 (1개)**
- [ ] 라벨러 A·B 배정 (제안: A는 @vmaca123, B는 다른 팀원 1명). 장준서는 라벨러에서 제외

## 8. 한계

- 라벨 규칙을 아무리 엄격히 해도 라벨러의 판단은 남는다. 일치도로 그 크기를 보여 줄 뿐이다.
- 계열 분할은 원본의 계열을 얼마나 잘 찾느냐에 달려 있다. 계열을 놓치면 유출이 생긴다.
- 통계 검정은 사례 수가 충분할 때만 의미가 있다. 사례 수를 보고서에 항상 함께 적는다.
